# Fauxcasa 0.1.0 — See your library again

Fauxcasa 0.1.0 is a read-only Picasa-library browser: point it at a folder
tree that Picasa used to manage and it shows you the same photos, folders,
albums, people, stars, and captions again. Normal browsing never writes into
your photo library. It does not edit, tag, export, or write anything back to
Picasa — this release is entirely about looking, not changing. (The optional
`--promote`, `--add-root`, and `--import-picasa-watched` CLI commands, and the
first-run "Use Picasa's watched folders" button, do write into the library —
see "Files this app writes" below.)

## Download

- Windows: `fauxcasa-0.1.0-windows-x64.zip`
- Linux: `fauxcasa-0.1.0-linux-x64.tar.gz`

## Verify

Each release archive is published alongside a `SHA256SUMS` file. Check the
download's hash against it:

```
# Windows (PowerShell or cmd)
certutil -hashfile fauxcasa-0.1.0-windows-x64.zip SHA256

# Linux/macOS
sha256sum fauxcasa-0.1.0-linux-x64.tar.gz
```

Compare the printed hash against the matching line in `SHA256SUMS`.

To confirm an archive was actually built by this project's CI (not
substituted or tampered with in transit), use GitHub's build provenance
attestation:

```
gh attestation verify fauxcasa-0.1.0-windows-x64.zip --repo maphew/fauxcasa
```

This proves CI provenance — that the file came from a GitHub Actions run in
this repository — but it does **not** make Windows trust the binary; see
SmartScreen below.

## Windows SmartScreen

The Windows build is unsigned, so SmartScreen will show an
unknown-publisher warning on first run. Right-click the downloaded zip,
open **Properties**, and click **Unblock** before **Extract All** — or, if
SmartScreen still intervenes at launch, click **More info** then
**Run anyway**.

## First run

The app window appears immediately; it does not wait for the library scan
to finish. The initial walk of your photo folder runs in the background
while the window is already up, and thumbnails fill in as they're indexed.

Fauxcasa never writes into your photo library during normal browsing. Its
own rebuildable catalog and thumbnail cache go to your user cache directory:

- Windows: `%LOCALAPPDATA%\Fauxcasa\cache`
- Other platforms: `$XDG_CACHE_HOME/fauxcasa`, or `~/.cache/fauxcasa` when
  `XDG_CACHE_HOME` is unset

## What works

- Folders (tree and flat view), albums (`.picasa.ini` and `.pal`), People
  and Unnamed faces, Starred, Recently Updated
- Ingest from `.picasa.ini`, `contacts.xml`, and db3 rescue sources
- Captions, keywords, stars (`Space` — stored locally in `stars.json`,
  never written back to the library), faces overlay (`F`), crops shown
- Hidden photos and folders (toggle: Show hidden)
- Search: multi-word AND, `-term` negation, over filename, caption,
  keywords, people, and folder names
- Selection tray: hold photos across folders (`Ctrl+H`)
- Stills including RAW (16 vendors) and PSD
- Video poster images and playback with audio (`P`, `Ctrl+Left`/`Ctrl+Right`
  seek)
- Viewer: 1:1 zoom (`1` / `Ctrl+Alt+0`) with pan, hover peek (`Ctrl+Alt`),
  slideshow (toolbar Play, per-folder header play)
- Info panel (`I`)
- Multi-root libraries via `--add-root` (CLI only)
- Offline-volume tolerance
- File Types panel (Tools menu)

## Files this app writes

Normal browsing never writes into your photo library or any Picasa file —
everything it writes lives under its own cache directory. The exception is
the small set of opt-in commands listed under "Written inside the library"
below.

Cache-root files (one set per machine):

- `config.json` — remembered library path, sort/view preferences, and File
  Types selections (per library, keyed by library path)
- `fauxcasa.log` — rotating diagnostic log (~4 MB ceiling)

Per-library files (one set per library, under a library-specific
subdirectory of the cache root):

- `catalog.json` (or `catalog.json.zst`) — the persisted scan catalog
- `thumbs.fcache` and `thumbs.fcache.json` — the thumbnail cache and its
  index
- `stars.json` — your star overrides, kept local, never written to the
  library
- `config.json` — per-library sort mode, flat/tree view choice, and the
  saved window geometry
- `import-report.json` — counts and notes from ingest (viewable from the
  status bar's import-notes button; see Known limitations)

Written inside the library (only by `--promote`, `--add-root`,
`--import-picasa-watched`, and the first-run "Use Picasa's watched
folders" button):

- `<root>/.fauxcasa/library.json` — `--promote` turns a plain folder into a
  multi-root library-home by writing this file inside the folder itself
  (`<root>/.fauxcasa/library.json`); `--import-picasa-watched` writes it at
  whatever library-home path you give it, which may or may not be inside a
  watched folder; `--add-root` rewrites the existing library-home's
  `library.json` in place rather than creating a new one. The first-run
  "Use Picasa's watched folders" button is the one exception that stays
  out of your library: it builds its library-home under the cache root
  instead (`picasa-watched-library/.fauxcasa/library.json`), so its
  `library.json` never lands inside a watched folder.
- `<root>/.fauxcasa-root` — a small id-recovery marker written into every
  root registered by `--promote`, `--add-root`, `--import-picasa-watched`,
  or the first-run "Use Picasa's watched folders" button (fail-soft: a
  write failure here doesn't stop the operation).

## Known limitations

- On Windows, still images (JPEG, PNG, GIF, BMP, TIFF, WebP, TGA) are
  decoded inside an AppContainer sandbox for thumbnails and the viewer;
  RAW, PSD, 16-bit TIFF and video are decoded in-process; on Linux
  everything is in-process. If the sandbox cannot start, the app says so
  in the status bar and decodes in-process. Force it required with
  `FAUXCASA_DECODE_SANDBOX=1` plus `--require-sandbox` (fails loud
  instead of degrading silently) or force it off with
  `FAUXCASA_DECODE_SANDBOX=0`. Only open libraries whose files you trust.
- On Windows, thumbnails of photos with a very tight Picasa crop (keeping
  less than about a seventh of the frame) are lower resolution than
  elsewhere, because the sandboxed thumbnail decode returns a bounded
  image size. The viewer shows the full-resolution crop as usual.
- At the smallest thumbnail size, fast scrolling of very large libraries on
  4K/high-DPI displays can stutter.
- Face regions stored inside image files (XMP `mwg-rs`), and captions or
  keywords stored inside RAW/TIFF files, are not read.
- Picasa's manual folder sort order is not read.
- Import notes are counted in the status bar, viewable in a dialog from
  there (or written to `import-report.json`), but there's no filtering or
  export of them yet.
- Videos have no 1:1 view.
- Starring is not available while a slideshow is running.
- macOS is not built (no hardware available to build/test on).
- The Windows build is unsigned — see SmartScreen above.
- Linux ships as a `tar.gz` built on Ubuntu 22.04 (glibc ≥ 2.35), and needs
  system `libxcb-cursor0 libxkbcommon-x11-0` plus GL/EGL and fontconfig
  libraries; alternatively run from source with
  `uv run apps/desktop-python/main.py ~/Pictures`.

## Where 0.1 stands against the M1 definition

The product spec's M1 gate ("See your library again") has three clauses:

1. **N4 budgets green on the 100k synthetic library.** Mostly green;
   scrolling at minimum zoom on high-DPI displays remains over budget
   (tracked: `fauxcasa-q6l.27`).
2. **`picasa_db.py survey` cross-check shows zero ingest loss on synthetic
   corpora.** Green in CI (`scripts/check-ingest-parity.py`).
3. **Owner confirms the same on the family archive.** Not yet recorded —
   this is a pending owner action (tracked: `fauxcasa-6g8`). See
   `docs/m1-gate-confirmation.md` for the runbook and confirmation record.

## Privacy when reporting a bug

Do not include photos, `.picasa.ini`/`.pal`/`contacts.xml`/db3 file
contents, real names, or real filesystem paths in a bug report. Do
include:

- The output of `fauxcasa.exe --version` (or `fauxcasa-console.exe
  --version`)
- Your OS and version
- A redacted copy of `fauxcasa.log` (strip paths and names before
  pasting)
